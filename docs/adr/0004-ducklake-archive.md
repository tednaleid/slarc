# The archive is a DuckLake: Parquet data files and a SQLite catalog

An archive stores Slack data as a DuckLake: Parquet data files under `data/` and a SQLite catalog, `catalog.sqlite`, beside downloaded files named by their content hash under `blobs/`. slarc reads and writes it through the `duckdb` package it already uses. A commit is one catalog transaction, so a batch is part of the archive if and only if its transaction committed. Tracked items and download states are rows updated in place, each tracked item carries a revision that every commit checks so a removal cannot be undone by a pull that started earlier, and `slarc rm` is a DELETE followed by maintenance that physically removes the bytes. Two `flock` locks in the XDG cache directory order writers and keep physical deletion away from running commands, and one machine owns an archive at a time. This supersedes ADR 0001. We chose it because the append-only JSONL design needed batches, commit lines, tags, dangling-line collection and sweeps to be safe under crashes, concurrent commands and removals, and most of that rebuilds what an open table format provides. The measurements and the failures behind each rule are in `docs/research/2026-10-20-ducklake-spike.md`, and the format comparison is in `docs/research/2026-10-20-open-table-formats.md`. The full design is `docs/specs/2026-10-20-ducklake-archive-design.md`.

## Considered Options

- Keep append-only JSONL and add a commit log (`docs/specs/2026-10-20-commit-log-design.md`): it works, but it is a hand-built transaction layer, and most of its cost existed to keep the archive mergeable in git. The spike measured the lake at 23% of the JSONL size, with search and conversation counts 2.7 to 3 times faster. - Iceberg: without a server, writes mean PyIceberg over a SQLite catalog that its docs mark as development only, while DuckDB's `iceberg` extension writes only through a REST catalog and calls itself experimental. PyIceberg has no data compaction and no orphan-file cleanup, deletes are copy-on-write, and it needs pyarrow (35 MiB) to write.
- Delta Lake: commits need no catalog and the format is stable, but each table commits on its own, so a message batch and its tracked-item update cannot be one atomic commit. Deletes are copy-on-write, physical removal waits on `vacuum` retention (7 days by default), the DuckDB `delta` extension only appends blindly, and delta-rs adds 45 MiB. The research doc compares them question by question.
- Plain SQLite as slackdump does: the research doc finds it meets crash safety and one-machine multi-process reads with the least machinery, but it has no file pruning, no time travel and no use on object storage. It was not benchmarked against the lake.

## Consequences

- Git is not supported. The archive is not meant to be merged or diffed, and blobs make an archive too large for a repository anyway. `rg`, `jq` and `cat` no longer read it directly; the archive is read through slarc (`search`, `sql`, `export`) or through DuckDB. A JSONL export can be added later if wanted.
- slarc does not import archives written in the JSONL layout and carries no JSONL code. The format was never released, and the only JSONL archives were the author's own. An archive with no `catalog.sqlite` and no files in `data/` or `blobs/` gets an empty lake, and any JSONL files in it are ignored. The recorded test fixture stays JSONL so it stays reviewable, and test code loads it into a lake.
- Edit history lives in `message_version` rows, which are kept. Snapshots are expired at every idle maintenance, so there is no time travel.
- Physical deletion uses no time windows. DuckLake's `older_than` windows proved unreliable in the spike, so deletion runs only when an exclusive read lock shows no other slarc command has the archive open.
- One machine opens an archive at a time. The catalog records the owning host by a stable machine id, every command checks it, and `--take-ownership` hands the archive over once a synced folder has finished syncing. The docs recommend local disk over a synced folder.
- Pinned dependency: `duckdb` is pinned exactly because the ducklake extension is built for one DuckDB release and the catalog does not migrate itself. The `ducklake` and `sqlite_scanner` extensions are downloaded on first use into the XDG cache, and an offline machine without them gets a plain error.
- DuckLake is young (spec 1.0 shipped on 2026-04-13). The design avoids the two behaviors the spike found worth reporting upstream, the time windows and the silent empty read after an expire, rather than relying on fixes.
- Storage stays behind the `ArchiveStore`, `QueryIndex` and `ArchiveLock` ports, so a different format later means new adapters, not new service code. `slarc sql` ties the command to DuckDB, not to DuckLake.
