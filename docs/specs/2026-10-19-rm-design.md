# `slarc rm`, quieter pulls of archived and not-visible conversations, and a retry cap for outside images

## Intent

An archive grows by pulling. Until now nothing could leave it: a conversation pulled by mistake, a thread no longer wanted, or a whole workspace stays tracked and stored for good. `slarc rm <selector>` is the one way to take something out. It stops tracking what the selector names and deletes what nothing still tracked needs.

There is deliberately no separate "untrack but keep" command. Ted's rule: if you want to keep something, don't remove it; if you want only part of the archive refreshed, name that part on `pull`. The two reasons to keep data while not refreshing it are handled by pull itself instead:

1. **A conversation Slack has archived** never changes, so pull stops refreshing it.
2. **A conversation the account can no longer see** warns once, then is skipped quietly.

## Goals

- **`rm` selectors:** `slarc rm` takes the same selectors as `pull` and `export`: a Slack link to a conversation, thread or message, `#channel-name`, `@user`, a conversation id, or a workspace name.
- **One rule for what is deleted:** `rm` deletes the stored messages that no remaining tracked item covers, and any downloaded files and images nothing left in the archive refers to.
- **Nothing half present:** after `rm`, a conversation is either fully stored or gone. A thread is never deleted out from under a conversation that is still tracked.
- **Archived conversations:** pull stops refreshing a Slack-archived conversation once its backfill is complete.
- **Not-visible conversations:** pull warns once when an item turns not visible, then skips it without warning until it is visible again.

## Non-goals

- **No "untrack but keep" mode, no `--keep` flag.**
- **Not undoable:** messages deleted from Slack since they were pulled cannot be recovered, and the prompt says so. Pulling the selector again re-tracks it and re-reads whatever Slack still has.
- **No running `rm` while a pull is running on the same archive.** No lock exists today and this design adds none. The CLI help says not to.

## Anti-goals (a failure even if it works)

- Deleting messages that a still-tracked item covers.
- A later pull re-downloading files for messages `rm` deleted.
- Leaving a month file half written after an interrupt or a full disk.
- Any Slack API call from `rm`. It is local only, like `export`.

## Behavior

### What a selector names
`rm` resolves a selector the way `pull` does, using the archive only:
- **A reply link** (one with `thread_ts`) names its thread item.
- **A message link** names the thread item or the message item at that ts, or both if both are tracked.
- **`--channel`** widens a message link to its conversation.
- **A workspace name** names every tracked item in that workspace.

What will be removed is listed in the confirmation prompt before anything changes.

### Coverage
A tracked item covers stored messages as follows:
- **conversation:** every stored message in that channel, regardless of its `since`/`until` range;
- **thread:** the parent at `ts` and every stored message whose `thread_ts` equals `ts`;
- **message:** the stored message at `ts`.

`rm` works in this order:
1. Resolve the selector to tracked items, using the archive only.
2. Mark those items removed.
3. Compute coverage from the items still tracked.
4. Delete every stored message line (message versions and deleted markers) in the affected channels that is not covered.

**A selector that names nothing tracked or removed** fails with one sentence, for example `Nothing tracked matches #foo.` This includes a message link to a stored message that is not itself a tracked item: `rm` removes tracked items, not arbitrary messages.

**A selector that names only items already removed** is accepted. It removes nothing new and runs the cleanup sweep below, so a crashed `rm` can be finished by running it again.

### Order of writes and recovery
`rm` keeps one invariant: every stored message is covered by some tracked item. Pull only ever stores covered messages: a thread read stores its parent and replies, and a conversation read stores messages of that conversation. `rm` works in this order:

1. **Append the `rm` run line first, and flush it.** It marks the items `removed` and records the final download states. From then on the removal is decided, even if the process dies.
2. **Sweep.** In every channel of every affected workspace, delete stored message lines that no remaining tracked item covers. Then delete file and image directory lines nothing references, and then blobs nothing references, as described below.

A crash during the sweep leaves uncovered lines and blobs on disk but never a tracked item with a gap. Running the same `rm` again finishes the sweep. Before the run line is written, nothing has changed.

The sweep is idempotent and only ever deletes what the invariant says is uncovered, so running it extra times is harmless.

**Untracked messages in a removed channel:** messages stored in an affected channel but covered by no item at all (possible after earlier `rm` runs or older archives) are deleted with that channel.

### Examples
- **`rm <thread link>` while `#general` is tracked:** the thread item is removed and no lines are deleted. Output: `Stopped tracking 1 item; kept 14 messages that other tracked items cover.`
- **`rm '#general'` while two of its threads are tracked:** `#general` is removed, and every message except those two threads' parents and replies is deleted.
- **`rm acme`:** every tracked item in workspace acme is removed and all its stored messages are deleted. With nothing in that workspace still tracked, its directory lines (users, emoji, conversations, bots, user groups, files, images) are deleted too.
- **`rm '#general'` when `#general` is the last tracked item in its workspace:** the result is the same as removing the whole workspace. The rule is "nothing tracked needs it", whatever selector was used. The workspace then disappears from `slarc list` and from export's workspace names.

### Files and images
After message lines are deleted, within each affected workspace:
- **Directory lines:** a `file` or `image` directory line whose target no remaining stored message references is deleted. That means every version of that target's line, with `directory/<team>/files.jsonl` and `images.jsonl` rewritten the same way as month files.
  - "References" means what pull's download collection uses: a message's `files`, image URLs, attachments and previews, counted across every stored version of each message.
  - User avatars and custom emoji images stay unless nothing in the workspace is tracked anymore.
- **Blobs:** a blob under `blobs/sha256/` that no remaining directory line in any workspace references is deleted. Blobs are shared by content, so one still used elsewhere stays.
- **Downloads:** each download target whose directory line is deleted gets a final state in the `rm` run line, including pending image downloads that never had a directory line. It uses a new status that pull's requeue skips.
  - Without it, `outstanding_downloads` would treat the missing line as outstanding and fetch it again.
  - A message pulled later that references the same target queues it afresh, so a re-tracked item downloads its files again.

### Confirmation
`rm` always shows a summary and asks before changing anything, for example:

```
Stop tracking 3 items and delete 2,470 lines, 85 files and 12 images?
Messages deleted from Slack since they were pulled cannot be pulled again. [y/N]
```

The default is No. `--yes` skips the prompt. When nothing will be deleted, it still confirms the untracking, without the warning line. Declining changes nothing and exits 1 with `Nothing removed.`, matching `No archive created.`

### Recording
- **The run line:** `rm` appends a run line (`command: "rm"`) with the removed items, their `status` set to the new value `removed`, and the download states above.
- **Removed items:** `ArchiveStore.tracked_items()` returns only items whose latest status is not `removed`, so every caller that means "tracked" (bare pull, workspace selectors, list, export's workspace expansion, coverage) gets the right set without its own filter. A new `ArchiveStore.removed_items()` returns the removed ones, for `rm` to accept selectors naming them.
- **Re-tracking:** pulling a removed item's selector again records it with `status: ok` as a new item. A new conversation item starts a fresh backfill.

### Rewriting files
Deleting lines rewrites only the files that lose lines: month files `raw/<team>/<channel>/<YYYY-MM>.jsonl`, and `directory/<team>/files.jsonl` and `images.jsonl`.
- Each file is written to a temp file in the same directory, fsynced, then renamed over the original. An interrupt leaves either the old file or the new one.
- A file left with no lines is deleted, and an empty channel directory is removed.
- Whole-workspace removal deletes `raw/<team>/` and `directory/<team>/` outright.

This is the only place slarc rewrites archive files. Every other write stays append-only.

### Archived conversations
A conversation archived since the last pull may have received messages before it was archived. So the skip starts only after one complete pull has run while the conversation was archived:

- **The flag:** `TrackedItem` gains `archived: bool = False`.
- **Setting it:** a pull that finds the conversation archived (`is_archived: true` in the conversation info just read) refreshes it as usual, including its backfill, search, active threads and `retry_threads`. If that pull finishes the item, it records `archived: true`.
- **Skipping:** a later pull that finds the item `archived: true` and the conversation still archived records the item as pulled without reading history, searching or re-reading threads. Its bar shows `0 read, 0 new`.
- **Unarchiving:** when the conversation is no longer archived, pull records `archived: false` and refreshes it as usual.
- **`--full`** re-reads an archived conversation anyway.

### Not-visible conversations
- **Warning once:** a `NotVisible` read warns only when the item's recorded status was `ok`, meaning it just turned not visible. An item already `not_visible` is skipped without a warning.
- **Where it shows:** `slarc list` shows its status, and the summary adds a line such as `1 item not visible to this account; see slarc list.`
- **Becoming visible again:** each pull still tries the item (directory refresh calls `conversations.info`). When it reads successfully, it returns to `ok` and is pulled as usual.

### Giving up on outside-site images
A download that is not a Slack file (`slack_auth` false: link previews, attachment images and other outside-site images) and fails 3 times stops being retried.

- **Today:** 403 and 404 are already terminal (`forbidden`). Timeouts and connection errors are `failed` and are requeued on every pull forever.
- **The change:** when such a download settles as `failed` with `attempts` reaching `OUTSIDE_MAX_ATTEMPTS = 3`, it settles as a new status `gave_up` instead.
  - `gave_up` joins `SKIPPED_STATUSES`, so the summary, the downloads bar and `slarc list` count it as skipped.
  - A normal pull never requeues it.
  - Slack file downloads (`slack_auth` true) keep retrying without a cap, because their failures usually mean an expired session the user can fix.
- **`--full`:** a pull with `--full` requeues `gave_up` and `forbidden` downloads of outside-site images, resetting `attempts` to 0. It only requeues those referenced by messages in the items being pulled, which `queue_downloads` already sees when it walks them. `too_large` keeps its existing rule: requeued when the limit now fits.

## Constraints

- **Layering:** the domain and service layers stay free of filesystem access. Rewriting month files, deleting directories and deleting blobs go through new `ArchiveStore` and `BlobStore` port methods, with in-memory fakes and contract tests against the real adapters.
- **Help:** `slarc rm` appears in the CLI help next to `pull` and `export`, with the same selector help text.
- **Docs:** `GLOSSARY.md` gains no new term unless the builder finds one is needed. The spec (`docs/specs/detailed-requirements.md`) and `docs/architecture.md` are updated to describe `rm`, the `removed` status, the archived skip and the not-visible behavior.

## Decided by Ted
- One command, named `rm`, with no separate untrack.
- `rm` deletes only what no remaining tracked item covers.
- The archived-conversation skip and the quieter not-visible handling ship in the same change.
- Outside-site images stop being retried after 3 failed attempts, and `--full` retries them. This ships in the same change.

## My calls (Claude), open to Ted's correction
- A conversation item's coverage ignores its date range.
- `rm` of a message link that is not a tracked item fails, not deletes the message.
- Default answer No on the prompt; `--yes` to skip it.
- A conversation found archived gets one more full refresh before the skip starts. A first pull of an archived conversation still backfills, and `--full` overrides the skip.
- Avatars and custom emoji images are deleted only when nothing in the workspace is tracked anymore.
- `rm` resolves selectors exactly as `pull` does. A reply link removes its thread item, and a link at a ts with both a thread item and a message item removes both.
- Removing the last tracked item in a workspace by any selector deletes the workspace's directory too.
- The run line is written first, then the sweep. A crash is finished by running `rm` again, which accepts selectors naming already-removed items.
- `files.jsonl` and `images.jsonl` are rewritten the same way as month files when their lines are deleted.
